# 仓库边界与 Desktop 开发准备

## 当前真实边界

| 位置 | 角色 | 说明 |
| --- | --- | --- |
| `backend/app/regintel`、`backend/app/api/regintel.py` | Cloud | 公共法规抓取、版本、检索和同步 HTTP API。 |
| `backend/app/local_regulations`、`backend/app/tenant`、Product Twin/Finding 模型 | Local | 私人上下文、法规缓存、重评估与本地 SQLite。 |
| `backend/app/entrypoints/{cloud,local,web}.py` | 运行入口 | 分别启动 Cloud、Local 和遗留 Web 托管模式。 |
| `frontend/` | 遗留 Web UI | 有可复用 React/Vite 组件，不是 Desktop 壳。 |
| `api/index.py`、`vercel.json` | 遗留 Web 部署适配器 | 仅把 Vercel 请求转发至 `backend/app/main.py`，没有重复业务实现。 |
| `apps/desktop/` | Desktop 准备区 | 新桌面壳和桌面 UI 只能从这里开始。 |
| `backend/alembic*` | 数据库迁移 | 常规链面向 Web/Local；`alembic_cloud` 仅面向 Cloud 法规库。 |
| `docker-compose*.yml`、`backend/Dockerfile*` | 基础设施 | Web 兼容 Compose 与 Cloud 专用部署分别保留。 |

`.aws/`、`.agents/`、`.codex/` 在当前工作树没有受 Git 跟踪的项目配置文件；未删除，以免误伤本机工具状态。`启动DataShield.bat` 是旧 Web 开发启动器，因仍可能被用户使用而保留，不是 Desktop 启动方式。

## 已确认的历史问题

- Cloud 以前错误使用完整 Alembic 链；现已由 `alembic-cloud.ini` 和 `alembic_cloud/` 隔离。
- Cloud Compose 以前只有 `internal` 网络，无法保证外部来源抓取；现拆为私有数据库网络和 Cloud 出站网络。
- Local runtime token 原先无法交给桌面壳；现在由用户目录 `runtime.json` 提供。

## 本轮未做的高风险迁移

未将 `backend/`、`frontend/`、Vercel 适配器或旧 Compose 机械移动到建议 Monorepo 路径：它们仍有测试、Docker、Vercel 和 Windows 启动器引用。Desktop 开发不受此阻塞；待桌面壳实际落地后，再通过受控迁移替换 Web 资源。
